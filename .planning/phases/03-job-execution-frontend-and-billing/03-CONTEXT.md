# Phase 3: Job Execution, Frontend, and Billing - Context

**Gathered:** 2026-03-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Wire GPU job dispatch, real-time status monitoring, results delivery, and Stripe billing into a working end-to-end flow. A scientist can launch a validated job (from Phase 2's JobSpec), watch its status in real time, download ranked PDB structures and a design report, and be charged accurately for GPU compute consumed.

Requirements covered: JOB-01, JOB-02, JOB-03, RESULT-01, RESULT-02, RESULT-03, BILL-01, BILL-02, BILL-03, BILL-04.

</domain>

<decisions>
## Implementation Decisions

### Job status & monitoring
- **Dual display**: Status updates stream into the existing agent chat (completion card with summary) AND a dedicated `/jobs/{id}` page exists for returning later
- **Stage-based progress**: Show discrete stages (Queued → Initializing GPU → Running diffusion → Scoring designs → Complete), not percentage. GPU tools don't reliably report % progress
- **Separate SSE endpoint**: Dedicated `/jobs/{id}/status` SSE stream for job status. Agent chat SSE handles conversation, job SSE handles status. Works on both chat and job page
- **One job at a time**: User must wait for current job to finish or cancel before launching another. Matches Phase 2's "one session at a time" pattern
- **Cancellation**: Confirm dialog ("This will stop GPU compute and you'll be charged for time consumed. Cancel?") then immediate kill
- **Job failure**: Error card with failure category (GPU timeout, invalid input, provider error) + agent guidance on what to fix. No auto-retry (per requirements — masks config errors, burns GPU without consent)
- **Email notifications**: Simple text + link via Resend (already set up for auth emails). "Your [tool] job is complete. 12 designs generated in 45 min. View results: [link]"
- **Job history**: Simple list of all past jobs with status badges on the job page. User can click into any job to see results. (Full job history page with filtering is v2: JOB-V2-01)
- **Navigation on completion**: Agent posts completion card in chat with top-level summary (# designs, cost, runtime) and a "View full results" button to `/jobs/{id}`. User stays in chat context

### Results & download
- **Structured card layout**: Results page as a series of cards — Run Summary card (tool, runtime, cost, parameters), then individual Candidate cards ranked by primary score
- **Tool-native scoring**: Display each tool's native scores — RFdiffusion pAE/pLDDT, BindCraft binding energy + iPAE, BoltzGen confidence. Rank position shown. Scientists know these metrics
- **Pre-ranked only**: Designs shown in rank order by primary score. No sort/filter controls in v1. Scientists download and analyze in their own tools
- **Download options**: "Download all designs" button generates a zip of all ranked PDBs + summary report text file. Each candidate card also has an individual download button
- **Next-step guidance**: "Recommended Next Steps" card at bottom of results page — suggests AlphaFold validation, expression system, synthesis partners. Static content generated by agent at job completion, stored with results
- **No 3D viewer in v1**: Results show scores, metadata, and download buttons only. Mol* viewer is explicitly v2 (RESULT-V2-01)
- **BindCraft zero-output**: Distinct "no designs" state card — "BindCraft completed but 0 designs passed filters. This is expected with strict criteria." Agent guidance suggests loosening parameters. User is still charged for GPU time (documented behavior)
- **30-day retention**: Results stored in R2/MinIO for 30 days. Warning banner when expiring soon. After expiry, job metadata stays in DB but files are deleted

### Billing & payment flow
- **Payment gate**: Payment method required only when user clicks "Launch job" — not at signup. Stripe Checkout redirect to add card. Lower friction to try the product
- **Cost estimate**: Range estimate ("$X–$Y estimated GPU cost") shown on the pre-launch review card (Phase 2's ReviewData). Range based on typical runtime for tool + parameters. Clear disclaimer that actual charge may differ
- **Pricing model**: Actual GPU cost + fixed percentage markup. User sees "GPU: $X, Platform fee: $Y, Total: $Z"
- **Cancelled job billing**: Charge for actual GPU time consumed up to cancellation. Clear in the cancellation confirmation dialog
- **Post-job cost display**: Results page shows "GPU cost: $X.XX (42 min on A100)" in the run summary card. Stripe sends its own receipt email automatically. No custom billing dashboard in v1
- **Stripe Billing Meters**: Report actual GPU-seconds consumed when job completes/cancels. Stripe meters aggregate and price per unit. 1 meter event = 1 job completion. Markup applied at the Stripe pricing tier level
- **Stripe Checkout**: Redirect to Stripe-hosted payment page for adding payment method. Handles PCI compliance, 3DS, all edge cases. Return to app after success
- **Stripe Customer Portal**: "Manage payment" link in account settings opens Stripe's hosted Customer Portal for card updates and invoice history. Zero custom billing UI

### GPU dispatch architecture
- **RunPod GPU Pods**: Dedicated pod instances via the Pod REST API. Long runtimes (30 min - hrs) make serverless unsuitable. Backend creates pods, containers run pipelines, POST results to webhook, backend terminates pod
- **GPUProvider ABC**: Abstract `GPUProvider` interface with `submit_job()`, `get_status()`, `cancel_job()`, `get_results()` methods. `RunPodProvider` implements it using the Pod API (`POST /v1/pods`, `DELETE /v1/pods/{id}`)
- **Background worker**: Job launch writes to DB + enqueues to Redis. Separate worker process picks up jobs, calls GPU provider, publishes status updates via Redis pub-sub. Decoupled from web server
- **A100 80GB default**: Standard for protein design workloads. All tools fit in 80GB VRAM
- **No hard timeout**: Jobs run to completion or until provider-level limit. Phase 4 adds watchdog for stuck containers
- **Pre-built Docker images**: One image per tool (RFdiffusion, BindCraft, BoltzGen, RFantibody) with all dependencies baked in. Push to Docker Hub or RunPod registry. Cold start is just image pull
- **Direct upload to R2**: Container uploads output PDBs directly to R2/MinIO using presigned URLs generated by the backend before dispatch. No intermediate hop through web server
- **RunPod webhooks**: RunPod calls a webhook endpoint on job completion/failure. Worker handles the callback, updates DB, publishes to Redis pub-sub for SSE. No polling loop
- **Idempotency**: Job state (status=queued) is written to the database before any GPU provider API call. Prevents double-billing on retry (BILL-04 requirement)

- Worker process management (standalone script, process manager, or containerized)
- Exact SSE event payload structure for job status
- Zip file generation approach (streaming vs in-memory)
- Email template formatting details
- Presigned URL expiry duration
- Exact stage names and transitions per tool
- Job history list pagination approach

<specifics>
## Specific Ideas

- RunPod webhooks eliminate polling — cleaner architecture than Phase 4's watchdog will need to handle
- Presigned URLs for direct RunPod → R2 upload keeps the backend stateless for large file transfers
- Stripe Billing Meters API (not legacy Usage Records) — report GPU-seconds, let Stripe handle aggregation and invoicing
- Stripe Checkout for payment collection + Customer Portal for management = zero custom billing UI
- BindCraft zero-output is documented expected behavior — the UX must not present it as a failure
- The Phase 2 ReviewData already includes `estimated_cost_usd` — Phase 3 extends this with the range estimate and billing flow
- Job stage names should be tool-specific where relevant (e.g., "Running diffusion" vs "Running binding optimization")

</specifics>
