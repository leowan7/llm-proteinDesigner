## Summary

Phase 3 connects five largely independent subsystems: GPU dispatch via RunPod, a background worker process, Redis pub/sub for real-time status fanout, a results delivery layer backed by R2/MinIO, and Stripe billing. Each subsystem is well-understood individually; the primary engineering risk is the integration seams — specifically the webhook → DB → Redis pub/sub → SSE chain and the Stripe billing flow around cancellations.

The existing codebase provides strong foundations. Redis 7.3.0 is already running in docker-compose. The `redis` Python package (7.3.0) supports async pub/sub natively via `redis.asyncio`. The storage client is boto3-based and already configured for S3v4 signatures, making presigned URL generation a one-call extension. The SSE streaming pattern (fetch + ReadableStream, not EventSource) is already established in `frontend/src/lib/agent.ts` and must be replicated for the job status endpoint.

**Primary recommendation:** Implement the worker as a standalone Python script using `arq` 0.27.0 for queue management, Redis pub/sub for status broadcast, and a thin `GPUProvider` ABC with `RunPodProvider` as the first concrete implementation. Wire Stripe Checkout for payment collection and Stripe Billing Meters for per-job charging. All five subsystems can be developed in parallel waves.

### Pattern 1: Job Launch Flow (BILL-04 Compliance)

The DB write MUST precede the RunPod API call. This is the idempotency guarantee.

**What:** Write `status=queued` to DB, then enqueue arq task, then the worker calls RunPod.
**When to use:** Every job launch without exception.

```python
# backend/jobs/dispatch.py
async def launch_job(job_id: str, job_spec: JobSpec, user_id: str, pool: asyncpg.Pool) -> None:
    """
    Write job to DB with status=queued BEFORE any GPU provider call.
    BILL-04 compliance: prevents double-billing on retry.
    """
    async with pool.acquire() as conn:
        await conn.execute(
            """
            UPDATE public.jobs
            SET status = 'queued', job_spec = $1::jsonb, updated_at = NOW()
            WHERE id = $2 AND user_id = $3
            """,
            job_spec.model_dump_json(),
            job_id,
            user_id,
        )
    # DB write confirmed — now safe to enqueue
    redis_client = await get_redis()
    await arq.create_pool(RedisSettings.from_url(settings.redis_url))
    await pool.enqueue_job("run_job", job_id=job_id)
```

### Pattern 2: Worker Task with GPU Provider

**What:** arq task that submits the RunPod job, handles webhook-triggered status updates, and publishes to Redis pub/sub.
**When to use:** All GPU job execution.

```python
# backend/worker/tasks.py
async def run_job(ctx: dict, job_id: str) -> None:
    """
    arq task: submit job to RunPod, update DB status, publish to Redis pub/sub.
    Webhook endpoint (not polling) handles completion/failure callbacks.
    """
    provider = RunPodProvider(api_key=settings.runpod_api_key)

    # Fetch job spec from DB
    spec = await get_job_spec(job_id)

    # Update DB: initializing
    await update_job_status(job_id, "running", stage="Initializing GPU")
    await publish_status(job_id, "running", "Initializing GPU")

    # Generate presigned PUT URLs for output upload
    output_prefix = f"users/{spec.user_id}/jobs/{job_id}/outputs/"
    presigned_urls = generate_presigned_put_urls(output_prefix, count=spec.parameters["num_designs"])

    # Submit to RunPod with webhook URL
    runpod_job_id = await provider.submit_job(
        endpoint_id=ENDPOINT_IDS[spec.tool],
        input_payload={
            "job_spec": spec.model_dump(),
            "output_presigned_urls": presigned_urls,
        },
        webhook_url=f"{settings.app_base_url}/webhooks/runpod",
    )

    # Persist RunPod job ID for cancellation
    await store_runpod_job_id(job_id, runpod_job_id)
    await publish_status(job_id, "running", "Running diffusion")
```

### Pattern 3: Redis Pub/Sub → SSE Fan-out

**What:** Worker publishes status events to Redis channel `job:{job_id}:status`. The FastAPI SSE endpoint subscribes and streams to the browser.
**When to use:** All real-time job status updates.

```python
# Source: verified against redis.asyncio documentation
# backend/jobs/router.py

@router.get("/{job_id}/status")
async def job_status_stream(job_id: str, user_id: str = Depends(get_current_user)):
    """Stream job status events via SSE using Redis pub/sub."""

    async def event_generator():
        r = redis.asyncio.from_url(settings.redis_url)
        pubsub = r.pubsub()
        await pubsub.subscribe(f"job:{job_id}:status")

        try:
            async for message in pubsub.listen():
                if message["type"] == "message":
                    yield f"data: {message['data'].decode()}\n\n"
                    data = json.loads(message["data"])
                    if data.get("status") in ("complete", "failed", "cancelled"):
                        break
        finally:
            await pubsub.unsubscribe(f"job:{job_id}:status")
            await r.aclose()

    return StreamingResponse(event_generator(), media_type="text/event-stream")


# Worker publishes like this:
async def publish_status(job_id: str, status: str, stage: str) -> None:
    r = redis.asyncio.from_url(settings.redis_url)
    payload = json.dumps({"status": status, "stage": stage, "job_id": job_id})
    await r.publish(f"job:{job_id}:status", payload)
    await r.aclose()
```

### Pattern 6: Presigned PUT URL for Direct Container Upload

**What:** Backend generates a presigned PUT URL before dispatching job. RunPod container uploads PDB files directly to R2, bypassing the web server.
**When to use:** All job output file uploads.

```python
# Extension of backend/storage/client.py
def generate_presigned_put_url(key: str, expires_in: int = 3600) -> str:
    """
    Generate a presigned PUT URL for direct upload to R2/MinIO.

    The RunPod container uses this URL to upload output PDB files directly
    without routing through the web server. Requires s3v4 signature (already
    configured in get_s3_client()). Expiry of 1 hour is sufficient for
    protein design jobs (typical runtime 15-60 min).

    Args:
        key: S3 object key, e.g. users/{uid}/jobs/{jid}/outputs/design_001.pdb
        expires_in: URL validity in seconds (default 3600 = 1 hour)

    Returns:
        Presigned URL string for HTTP PUT upload.
    """
    client = get_s3_client()
    return client.generate_presigned_url(
        "put_object",
        Params={"Bucket": settings.s3_bucket_name, "Key": key},
        ExpiresIn=expires_in,
    )
```

### Pattern 7: Zip Download (RESULT-01)

**What:** Stream a zip of all ranked PDB files + summary report from R2 to the browser.
**When to use:** "Download all designs" button.

```python
# backend/jobs/router.py
@router.get("/{job_id}/download")
async def download_all_designs(job_id: str, user_id: str = Depends(get_current_user)):
    """
    Stream a zip file of all ranked output PDBs and the summary report.
    Uses in-memory BytesIO — acceptable for protein design outputs
    (10-50 PDB files at ~100KB each = 1-5 MB total; well within memory budget).
    """
    import io
    import zipfile

    s3 = get_s3_client()
    prefix = f"users/{user_id}/jobs/{job_id}/outputs/"

    # Fetch list of output files from R2
    objects = s3.list_objects_v2(Bucket=settings.s3_bucket_name, Prefix=prefix)

    buffer = io.BytesIO()
    with zipfile.ZipFile(buffer, "w", compression=zipfile.ZIP_DEFLATED) as zf:
        for obj in objects.get("Contents", []):
            body = s3.get_object(Bucket=settings.s3_bucket_name, Key=obj["Key"])["Body"].read()
            filename = obj["Key"].split("/")[-1]
            zf.writestr(filename, body)

    buffer.seek(0)

    return StreamingResponse(
        iter([buffer.read()]),
        media_type="application/zip",
        headers={"Content-Disposition": f'attachment; filename="job_{job_id}_designs.zip"'},
    )
```

### Pattern 9: RunPod Webhook Handler

RunPod posts to your webhook URL on job completion/failure. The handler must:
1. Validate HMAC signature
2. Parse RunPod job state
3. Update DB
4. Publish to Redis pub/sub
5. Trigger Stripe meter event

```python
# backend/webhooks/router.py
# RunPod job states: IN_QUEUE, RUNNING, COMPLETED, FAILED, CANCELLED, TIMED_OUT
# Source: docs.runpod.io/serverless/references/job-states (verified)

@router.post("/runpod")
async def runpod_webhook(request: Request):
    """
    RunPod calls this endpoint on job completion, failure, or status change.
    Retries up to 2 times with 10-second delay if we return non-200.
    Must return 200 promptly; do heavy work async.
    """
    body = await request.body()
    # Validate HMAC-SHA256 signature from X-RunPod-Signature header
    validate_runpod_signature(body, request.headers.get("X-RunPod-Signature"))

    payload = json.loads(body)
    runpod_job_id = payload["id"]
    runpod_status = payload["status"]   # "COMPLETED", "FAILED", "CANCELLED", "TIMED_OUT"

    # Map RunPod states to our internal states
    status_map = {
        "COMPLETED": "complete",
        "FAILED": "failed",
        "CANCELLED": "cancelled",
        "TIMED_OUT": "failed",
    }

    internal_status = status_map.get(runpod_status)
    if internal_status:
        job_id = await get_job_id_by_runpod_id(runpod_job_id)
        await update_job_status(job_id, internal_status)
        await publish_status(job_id, internal_status, stage=internal_status.capitalize())

        if internal_status in ("complete", "cancelled"):
            await trigger_billing(job_id)   # record Stripe meter event

        if internal_status in ("complete", "failed"):
            await send_completion_email(job_id)

    return {"received": True}
```

### Anti-Patterns to Avoid

- **Calling RunPod before DB write:** Violates BILL-04. If the process dies between RunPod call and DB write, job runs but is never tracked or billed.
- **Using EventSource for job status SSE:** EventSource is GET-only with no auth header support. The existing pattern (fetch + ReadableStream with cookie auth) must be replicated.
- **Polling RunPod for status:** The webhook architecture is the decided approach. Polling adds unnecessary latency and load.
- **Auto-retry on failure:** Explicitly out of scope. A failed job must surface a clear error; re-running without user consent masks config errors and burns GPU budget.
- **Using Stripe Usage Records:** Removed from Stripe API v2025-03-31. Use `stripe.billing.MeterEvent.create()` only.
- **Streaming file uploads through the backend:** The presigned URL pattern keeps the backend stateless for large files. Never proxy PDB file uploads through FastAPI.
- **Returning non-200 from RunPod webhook without immediate return:** RunPod retries only 2 times. Heavy async work must be enqueued (via arq or asyncio task), not done inline.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Payment method collection | Custom card form | Stripe Checkout `mode="setup"` | PCI compliance, 3DS, browser autofill — all handled by Stripe |

## Common Pitfalls

### Pitfall 1: Stripe Billing Meters Setup Requires Dashboard Configuration First

**What goes wrong:** `stripe.billing.MeterEvent.create(event_name="gpu_seconds", ...)` returns a 400 error: "No such meter for event_name 'gpu_seconds'."
**Why it happens:** The meter must be created in the Stripe Dashboard (or via API at first deploy) before meter events can be sent. The `event_name` in code must exactly match the configured meter's `event_name`.
**How to avoid:** Wave 0 setup task: create the billing meter via Stripe Dashboard or `stripe.billing.Meter.create()` script. Store the `event_name` value in `settings` so it can be changed without code changes. Also create the product, price, and subscription template.
**Warning signs:** 400 responses from Stripe with "No such meter" in the error detail.

---

### Pitfall 2: Stripe Customer Must Exist Before Checkout Session

**What goes wrong:** `stripe.checkout.Session.create(customer=None, mode="setup")` — Stripe creates an anonymous customer. The resulting payment method is not attached to the application user.
**Why it happens:** If the app doesn't create/store a Stripe customer ID at first billing interaction, the card is saved to a Stripe-managed ephemeral customer with no linkage to the user record.
**How to avoid:** At first billing interaction (before creating Checkout session), call `stripe.Customer.create(email=user_email, metadata={"user_id": user_id})` and store `stripe_customer_id` on the `users` table. Always pass `customer=stripe_customer_id` to Checkout and Portal sessions.
**Warning signs:** Payment methods not appearing in Customer Portal; meter events failing with "customer not found."

---

### Pitfall 3: Redis Pub/Sub SSE Connection Leaks

**What goes wrong:** Browser tab closes; SSE generator keeps running; Redis pub/sub subscription never unsubscribed.
**Why it happens:** FastAPI's `StreamingResponse` generator does not automatically detect client disconnection. Without explicit cleanup, pub/sub connections accumulate.
**How to avoid:** Use `try/finally` in the SSE generator to always unsubscribe and close the Redis connection. Also listen for `asyncio.CancelledError` as the signal that the client disconnected.
**Warning signs:** Growing number of Redis connections over time; `CLIENT LIST` shows many idle pub/sub connections.

---

### Pitfall 4: arq At-Least-Once Delivery Without Idempotent Workers

**What goes wrong:** Worker crashes between RunPod submit and storing the `runpod_job_id`. arq re-runs the task. Two RunPod jobs are submitted for one application job.
**Why it happens:** arq guarantees at-least-once delivery; tasks may run more than once if interrupted.
**How to avoid:** Check for an existing `runpod_job_id` in the DB at the start of the worker task. If already set, skip `submit_job()` and only poll status. This makes the task idempotent.
**Warning signs:** Duplicate RunPod charges; duplicate completion webhooks.

---

### Pitfall 5: RunPod Webhook Delivery Reliability

**What goes wrong:** RunPod webhook fails (network error, app down); job completes but DB never updates; user sees job stuck in "running."
**Why it happens:** RunPod retries only 2 more times with 10-second delay, then stops. If all three attempts fail, the job state is permanently lost unless there is a reconciliation mechanism.
**How to avoid:** Phase 3 accepts this risk (no watchdog until Phase 4). The immediate mitigation is to return 200 from the webhook handler as fast as possible (enqueue async work) and ensure the webhook endpoint has high availability. Document this as a known Phase 3 limitation.
**Warning signs:** Jobs stuck in "running" state with no corresponding active RunPod job.

---

### Pitfall 6: BindCraft Zero-Output Must Not Read as Failure

**What goes wrong:** Worker receives COMPLETED from RunPod but output directory contains 0 PDB files. Code treats this as an error and sets `status=failed`.
**Why it happens:** BindCraft returns COMPLETED even when all designs fail filters — this is expected behavior documented in the requirements.
**How to avoid:** Worker checks the output file count separately from the RunPod job status. Zero output files → set a `zero_output` flag in the results JSONB and `status=complete`. Frontend renders the distinct "BindCraft zero-output" card, not the failure card.
**Warning signs:** Users reporting billing for "failed" BindCraft jobs; missing Stripe meter events on BindCraft runs.

---

### Pitfall 7: Stripe `value` Field Must Be a String

**What goes wrong:** `stripe.billing.MeterEvent.create(payload={"value": 3600})` raises a Stripe validation error.
**Why it happens:** The Stripe Billing Meters API expects the `value` field in the payload to be a string, not an integer.
**How to avoid:** Always `str(gpu_seconds)` before passing to the payload dict.
**Warning signs:** Stripe returns 400 with "Invalid integer: value must be a string."

## Database Migration Required

Phase 3 needs new columns on `users` and `jobs`, plus a new table for design candidates.

**New migration: `20260319000002_billing_and_results.sql`**

```sql
-- Stripe customer ID on users
ALTER TABLE public.users ADD COLUMN IF NOT EXISTS stripe_customer_id TEXT;

-- Job execution tracking columns
ALTER TABLE public.jobs ADD COLUMN IF NOT EXISTS runpod_job_id TEXT;
ALTER TABLE public.jobs ADD COLUMN IF NOT EXISTS started_at TIMESTAMPTZ;
ALTER TABLE public.jobs ADD COLUMN IF NOT EXISTS completed_at TIMESTAMPTZ;
ALTER TABLE public.jobs ADD COLUMN IF NOT EXISTS gpu_seconds INTEGER;           -- actual compute time
ALTER TABLE public.jobs ADD COLUMN IF NOT EXISTS gpu_cost_usd NUMERIC(10,4);    -- final charge
ALTER TABLE public.jobs ADD COLUMN IF NOT EXISTS stage TEXT;                    -- current progress stage
ALTER TABLE public.jobs ADD COLUMN IF NOT EXISTS error_category TEXT;           -- GPU timeout | invalid input | provider error
ALTER TABLE public.jobs ADD COLUMN IF NOT EXISTS results JSONB;                 -- {candidate_count, next_steps, zero_output}

-- Design candidates (ranked outputs)
CREATE TABLE IF NOT EXISTS public.job_candidates (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    job_id      UUID NOT NULL REFERENCES public.jobs(id) ON DELETE CASCADE,
    rank        INTEGER NOT NULL,                    -- 1-based rank by primary score
    pdb_key     TEXT NOT NULL,                       -- R2 object key for PDB file
    scores      JSONB NOT NULL DEFAULT '{}',         -- tool-native scores: {pae, plddt, binding_energy, ...}
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_job_candidates_job_id ON public.job_candidates(job_id);
ALTER TABLE public.job_candidates ENABLE ROW LEVEL SECURITY;
CREATE POLICY candidates_own ON public.job_candidates
    FOR ALL USING (
        auth.uid() = (SELECT user_id FROM public.jobs WHERE id = job_id)
    );
```

**Note on `status` enum:** The existing `CHECK` constraint already includes `'queued'`, `'running'`, `'complete'`, `'failed'`, `'cancelled'`. No changes needed to the jobs status column.

## RunPod API Reference (Verified)

| Operation | Method | URL | Notes |
|-----------|--------|-----|-------|
| Submit async job | POST | `https://api.runpod.ai/v2/{endpoint_id}/run` | Returns `{id: job_id}`; include `webhook` in body |
| Check status | GET | `https://api.runpod.ai/v2/{endpoint_id}/status/{job_id}` | Returns status + output |
| Cancel job | POST | `https://api.runpod.io/v2/{endpoint_id}/cancel/{job_id}` | Returns `{id, status: "CANCELLED"}` |

**Job states (verified against docs.runpod.io/serverless/references/job-states):**
`IN_QUEUE` → `RUNNING` → `COMPLETED` | `FAILED` | `CANCELLED` | `TIMED_OUT`

**RunPod async submit request body:**
```json
{
  "input": { "job_spec": {}, "output_presigned_urls": [] },
  "webhook": "https://app.kendrew.ai/webhooks/runpod"
}
```

**RunPod webhook retry behavior:** Posts to webhook URL on terminal state. Retries 2 times with 10-second delay on non-200 response. Must return 200 within webhook handler immediately.

## Open Questions

1. **Stripe meter pricing tier setup**
   - What we know: Meter event_name and value units (gpu_seconds) are decided. Stripe aggregates events.
   - What's unclear: The exact markup percentage and the dollar-per-GPU-second price tier have not been set in the Stripe Dashboard. Without this, the meter event records correctly but generates $0 invoices.
   - Recommendation: Wave 0 setup task must include creating the Stripe Meter, Product, Price (with the markup), and a default Subscription template. This is a one-time Dashboard operation, not code.

2. **RunPod endpoint IDs per tool**
   - What we know: Pre-built Docker images, one per tool. RunPod serverless endpoints must be created per image.
   - What's unclear: The RunPod endpoint IDs for each tool image are not known until the images are deployed and endpoints registered. Code must reference these via config, not hardcoded.
   - Recommendation: Add `runpod_endpoint_rfdiffusion`, `runpod_endpoint_bindcraft`, etc. to `Settings`. Worker reads from settings at runtime.

3. **Stripe webhook handling for Checkout setup completion**
   - What we know: Stripe Checkout `mode="setup"` → user lands on success URL after saving card. The payment method is now attached to the Stripe customer.
   - What's unclear: Whether the app needs to listen to `checkout.session.completed` webhook event to confirm setup, or can simply check `stripe.Customer.retrieve(customer_id).invoice_settings.default_payment_method` before dispatch.
   - Recommendation: The simpler approach — check for a default payment method at dispatch time — is sufficient for v1. No webhook listener for Checkout needed.
