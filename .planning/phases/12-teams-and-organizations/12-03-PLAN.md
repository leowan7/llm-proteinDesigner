Every existing route that currently filters by user_id either becomes org-scoped (jobs, billing) or remains user-scoped but gains an active-org context for cross-org awareness (user). New signup auto-creates a personal org so the post-Wave-2 schema invariant holds: every user has exactly one personal org as their default.

The feature flag from Plan 12-02 still gates router mounting, so this plan can deploy without flipping the flag — that switch belongs to Plan 12-04's rollout step.

async def get_or_create_customer(
    email: str,
    org_id: str,
    org_name: str,
    pool: asyncpg.Pool,
) -> str:
    """Return the Stripe customer ID for an organization, creating one if needed.

    Phase 12: Stripe customer lives at the org level. Personal orgs (one per
    user, auto-created at signup) hold the customer ID that used to live on
    public.users.stripe_customer_id.

    Args:
        email: Billing contact email (owner's email or org's billing_email).
        org_id: Organization UUID.
        org_name: Organization name (used as Stripe customer metadata).
        pool: Database pool.

    Returns:
        Stripe customer ID (cus_...).
    """
    row = await pool.fetchrow(
        "SELECT stripe_customer_id FROM public.organizations WHERE id = $1",
        org_id,
    )
    if row and row["stripe_customer_id"]:
        return row["stripe_customer_id"]
    customer = stripe.Customer.create(
        email=email,
        metadata={
            "organization_id": org_id,
            "kendrew_org_name": org_name,
        },
    )
    await pool.execute(
        "UPDATE public.organizations SET stripe_customer_id = $1, updated_at = now() WHERE id = $2",
        customer.id, org_id,
    )
    return customer.id
```

async def _resolve_stripe_customer(org_id: str) -> str:
    """Resolve the Stripe customer ID for an organization, creating one if needed.

    Reads the deterministic-first owner's email as the billing contact (oldest
    owner membership wins; predictable for migrated personal orgs).
    """
    pool = await get_db_pool()
    async with pool.acquire() as conn:
        org_row = await conn.fetchrow(
            "SELECT id, name FROM public.organizations WHERE id = $1", org_id,
        )
        if org_row is None:
            raise HTTPException(status_code=404, detail="Organization not found")
        owner_row = await conn.fetchrow(
            """SELECT u.email FROM public.organization_memberships m
               JOIN public.users u ON u.id = m.user_id
               WHERE m.organization_id = $1 AND m.role = 'owner'
               ORDER BY m.created_at ASC LIMIT 1""",
            org_id,
        )
        if owner_row is None:
            raise HTTPException(
                status_code=409,
                detail="Organization has no owner; cannot resolve billing contact",
            )
    return await get_or_create_customer(
        email=owner_row["email"],
        org_id=str(org_row["id"]),
        org_name=org_row["name"],
        pool=pool,
    )
```

# Phase 12: Auto-create a personal organization for the new user so all
# downstream paths (jobs, billing, RLS) always have an org context.
try:
    pool = await get_db_pool()
    async with pool.acquire() as conn:
        async with conn.transaction():
            email_local = body.email.split("@", 1)[0] or "Personal"
            personal_name = f"{email_local} (Personal)"
            org_row = await conn.fetchrow(
                """INSERT INTO public.organizations (name, is_personal, created_by)
                   VALUES ($1, TRUE, $2)
                   RETURNING id""",
                personal_name, new_user_id,
            )
            await conn.execute(
                """INSERT INTO public.organization_memberships (organization_id, user_id, role)
                   VALUES ($1, $2, 'owner'::public.org_role)
                   ON CONFLICT DO NOTHING""",
                org_row["id"], new_user_id,
            )
except Exception as exc:
    logger.warning(
        "Signup succeeded for user %s but personal org bootstrap failed: %s",
        new_user_id, exc,
    )

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → /jobs/* | X-Org-Id header determines which org's jobs are visible; require_role enforces RBAC; jobs.organization_id is the RLS scope |
| client → /billing/* | Owner-only — non-owner members must see 403 even when X-Org-Id is valid |
| webhook (unauth) → record_gpu_usage | Webhook handler service-role pool bypasses RLS; must resolve customer via JOIN not user_id direct lookup |
| signup (unauth) → org bootstrap | Signup runs as service_role and writes the new user's org + membership; must not allow caller to inject an arbitrary user_id |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-03-01 | Spoofing | X-Org-Id header on /jobs | mitigate | require_role chains through get_active_org which cross-checks header against organization_memberships row |
| T-12-03-02 | Elevation of Privilege | Viewer launches job via launch_job_endpoint | mitigate | require_role("owner","scientist") on launch_job_endpoint returns 403 for viewer |
| T-12-03-03 | Information Disclosure | Viewer reads billing endpoints | mitigate | require_role("owner") on every billing endpoint returns 403 for scientist/viewer |
| T-12-03-04 | Tampering | Webhook handler routes meter to wrong customer | mitigate | JOIN through jobs.organization_id ties meter event to the same org that owned the job; integration test test_webhook_completion_resolves_customer_via_org_join verifies |
| T-12-03-05 | Information Disclosure | list_jobs leaks created_by_email to viewers | accept | created_by_email is the member's email shown to other org members — this is intended UX (RESEARCH §13 Q7) |
| T-12-03-06 | Tampering | Signup injects arbitrary user_id into org bootstrap | mitigate | new_user_id is taken from Supabase sign_up's result.user.id (server-side authoritative), never from request body |
| T-12-03-07 | Denial of Service | get_or_create_customer races on first job launch | accept | UPDATE public.organizations is idempotent; if two concurrent launches both create a Stripe customer, the second UPDATE wins and the unused customer is orphaned (Stripe cleanup job, not Phase 12) |
| T-12-03-08 | Repudiation | Job launched with no audit trail | mitigate | jobs.created_by_user_id NOT NULL; backfilled from existing user_id; new INSERTs populate it from get_current_user |
</threat_model>
