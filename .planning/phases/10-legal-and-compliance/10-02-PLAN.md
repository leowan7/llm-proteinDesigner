# Plan 10-02: ToS Acceptance on Signup + Retention Column + Re-Acceptance Gate

## Objective

Persist ToS acceptance on signup, force re-acceptance when the version bumps, and add the `data_retention_days` column that Plan 10-05's retention cron will read. This plan unblocks Plans 10-04 (GDPR endpoints) and 10-05 (retention cron).

## Scope

1. DB migration adds three columns to `public.users`: `tos_accepted_at TIMESTAMPTZ`, `tos_version TEXT`, `data_retention_days INT NOT NULL DEFAULT 90 CHECK (data_retention_days BETWEEN 30 AND 365)`.
2. Backend `/auth/signup` accepts a `tos_version` field on the request body, validates it equals `TOS_VERSION` (env-configured), and writes `tos_accepted_at = now()` + `tos_version` to `public.users` immediately after the Supabase `sign_up` call succeeds.
3. Backend `/user/me` (or `/auth/me`) returns `tos_version` and `tos_current` (the canonical version string the backend expects) so the frontend can detect version drift and show the re-acceptance modal. **This plan does NOT add `deletion_requested_at` to the /user/settings response — that field is owned by Plan 10-04 (wave 2)**.
4. Backend `POST /user/accept-tos` records re-acceptance for authenticated users without requiring a full signup.
5. Frontend `SignUp.tsx` adds a required "I agree to Terms of Service and Privacy Policy" checkbox gate plus two hyperlinks that open `/legal/terms` and `/legal/privacy` in a new tab.
6. Frontend `AuthenticatedLayout.tsx` renders `<ReAcceptanceModal>` as a blocking overlay when `/auth/me` reports `tos_version !== tos_current`.

## Threat Model

Trust boundaries: (1) unauthenticated browser → /auth/signup, (2) authenticated browser → /user/accept-tos, (3) DB row storing acceptance proof.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10.02-01 | Repudiation | /auth/signup | mitigate | Write `tos_accepted_at = now()` + `tos_version` + user_id in a single UPDATE inside the signup handler's existing Supabase-success branch. If UPDATE affects 0 rows, retry once after 200ms (trigger race) and log a warning; never 200 without a recorded acceptance for the new user. |
| T-10.02-02 | Tampering (downgrade) | SignUpRequest.tos_version | mitigate | Backend compares against `settings.tos_current_version` (server-side constant); request-supplied older versions are rejected with 400. Frontend always sends `TOS_VERSION` from the compiled bundle. |
| T-10.02-03 | Bypass (re-acceptance) | AuthenticatedLayout modal | mitigate | Modal is a blocking Dialog with no close affordance; `onOpenChange` is a no-op so user cannot dismiss. API calls from inside the layout still function, but UI navigation is obscured. Backend does NOT gate API endpoints on tos_current — modal is a UX signal, not a security control. Authoritative re-acceptance enforcement (blocking API calls) is deferred to a future hardening pass; acceptable for v1 because no data exfiltration path is opened by continued access. |
| T-10.02-04 | Info disclosure | /user/settings | accept | tos_version and tos_current are not sensitive; exposing them in /settings is acceptable. |
| T-10.02-05 | DoS | /user/accept-tos spam | mitigate | Existing `limiter` middleware applies; endpoint is cheap (single UPDATE). Not adding extra rate limits. |
