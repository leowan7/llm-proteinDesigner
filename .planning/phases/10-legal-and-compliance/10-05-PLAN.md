## Objective

Enforce the 90-day-by-default retention policy: expire uploaded structures, job outputs, and job rows past the per-user retention window; warn users 7 days before deletion; and expose a per-user override (30-365 days) in Settings.

## Scope

1. DB migration adds `retention_warning_sent_at TIMESTAMPTZ`, `retention_deleted_at TIMESTAMPTZ` to `public.jobs`. Also creates `public.retention_policy` single-row table tracking `policy_effective_from TIMESTAMPTZ` — set to migration apply time so pre-policy jobs are exempt unless opted in.
2. Daily arq cron at 04:45 UTC (offset from `refresh_live_stats` which runs at 04:30 UTC):
   - (a) Warning pass: find jobs where `created_at + interval '(retention_days - 7) days' < now()` AND `created_at > policy_effective_from` AND `retention_warning_sent_at IS NULL` AND `retention_deleted_at IS NULL` — send warning email, stamp `retention_warning_sent_at`.
   - (b) Deletion pass: find jobs where `created_at + interval 'retention_days days' <= now()` AND `retention_deleted_at IS NULL` AND `created_at > policy_effective_from` — delete S3 objects under `users/{user_id}/jobs/{job_id}/`, UPDATE row with `retention_deleted_at = now(), status = 'expired'` (if not already terminal), keep the row so users see the expiry note in job history.
3. Jobs with status still 'running' are NEVER deleted — cron skips non-terminal rows (safety guard against deleting active work).
4. `PUT /user/retention` endpoint with body `{data_retention_days: int}` (30-365) — updates the column. Returns `{data_retention_days: int}`.
5. Frontend `PrivacyTab.tsx` gains a "Data retention" section with a numeric input (30-365) + Save button.

    def delete_job_objects(user_id: str, job_id: str) -> int:
        """Delete all R2 objects under users/{user_id}/jobs/{job_id}/.

        Returns the count of objects deleted. Safe to call on an empty/missing prefix.
        Raises on permission errors.
        """
        client = get_s3_client()
        prefix = f"users/{user_id}/jobs/{job_id}/"
        deleted = 0
        paginator = client.get_paginator("list_objects_v2")
        for page in paginator.paginate(Bucket=settings.s3_bucket_name, Prefix=prefix):
            contents = page.get("Contents") or []
            if not contents:
                continue
            keys = [{"Key": obj["Key"]} for obj in contents]
            resp = client.delete_objects(
                Bucket=settings.s3_bucket_name,
                Delete={"Objects": keys, "Quiet": True},
            )
            deleted += len(keys)
            errors = resp.get("Errors") or []
            if errors:
                logger.error("delete_job_objects errors job=%s user=%s: %s", job_id, user_id, errors)
                raise RuntimeError(f"delete_objects reported {len(errors)} errors")
        logger.info("delete_job_objects: user=%s job=%s deleted=%d", user_id, job_id, deleted)
        return deleted
    ```

    """Retention cron — daily at 04:45 UTC (offset from refresh_live_stats at 04:30 UTC).

    Two passes:
      1. Warning: email owners 7 days before their retention deadline.
      2. Deletion: hard-delete object storage for expired jobs; stamp row.

    Policy:
      - Per-user `data_retention_days` (30-365, default 90).
      - Jobs created before `retention_policy.policy_effective_from` are EXEMPT —
        we do not retroactively delete pre-policy data. Users must opt-in to
        retroactive cleanup (future feature; out of scope here).
      - Running jobs are never touched. Terminal jobs are marked status='expired'.
    """
    import logging
    import datetime

    from db.connection import get_db_pool
    from storage.client import delete_job_objects
    from jobs.notifications import send_retention_warning_email

    logger = logging.getLogger(__name__)

    WARNING_DAYS_BEFORE = 7
    TERMINAL_STATUSES = ("complete", "failed", "cancelled")

    async def _fetch_policy_effective_from(pool) -> datetime.datetime:
        async with pool.acquire() as conn:
            row = await conn.fetchrow("SELECT policy_effective_from FROM public.retention_policy WHERE id = 1")
        if row is None:
            raise RuntimeError("retention_policy.id=1 missing — migration 20260424000003 not applied")
        return row["policy_effective_from"]

    async def send_retention_warnings(ctx: dict | None = None) -> int:
        """Pass 1 of retention cron: email owners 7 days before deletion."""
        pool = await get_db_pool()
        effective_from = await _fetch_policy_effective_from(pool)
        # Uniform f-string substitution for the INTERVAL constant (W8). All other values
        # are bound via $N parameters — only the compile-time WARNING_DAYS_BEFORE constant
        # is interpolated into the query text.
        query = f"""
            SELECT j.id, j.user_id, j.name, j.created_at,
                   u.email, u.data_retention_days
            FROM public.jobs j
            JOIN public.users u ON u.id = j.user_id
            WHERE j.retention_warning_sent_at IS NULL
              AND j.retention_deleted_at IS NULL
              AND j.created_at > $1
              AND j.created_at + (u.data_retention_days || ' days')::interval
                  < NOW() + INTERVAL '{WARNING_DAYS_BEFORE} days'
              AND j.created_at + (u.data_retention_days || ' days')::interval > NOW()
        """
        async with pool.acquire() as conn:
            rows = await conn.fetch(query, effective_from)
        sent = 0
        for row in rows:
            deletion_date = row["created_at"] + datetime.timedelta(days=row["data_retention_days"])
            try:
                await send_retention_warning_email(
                    to_email=row["email"],
                    job_id=str(row["id"]),
                    job_name=row["name"],
                    deletion_date_iso=deletion_date.date().isoformat(),
                    retention_days=row["data_retention_days"],
                )
                async with pool.acquire() as conn:
                    await conn.execute(
                        "UPDATE public.jobs SET retention_warning_sent_at = now() WHERE id = $1",
                        row["id"],
                    )
                sent += 1
            except Exception as exc:
                logger.error("send_retention_warnings: job=%s email failed: %s", row["id"], exc)
        logger.info("send_retention_warnings: %d warning(s) sent", sent)
        return sent

    async def execute_retention_deletions(ctx: dict | None = None) -> int:
        """Pass 2: hard-delete objects + stamp retention_deleted_at."""
        pool = await get_db_pool()
        effective_from = await _fetch_policy_effective_from(pool)
        async with pool.acquire() as conn:
            rows = await conn.fetch(
                """SELECT j.id, j.user_id, j.status, j.created_at, u.data_retention_days
                   FROM public.jobs j
                   JOIN public.users u ON u.id = j.user_id
                   WHERE j.retention_deleted_at IS NULL
                     AND j.status != 'running'
                     AND j.created_at > $1
                     AND j.created_at + (u.data_retention_days || ' days')::interval <= NOW()
                """,
                effective_from,
            )
        deleted = 0
        for row in rows:
            job_id = str(row["id"])
            user_id = str(row["user_id"])
            try:
                count = delete_job_objects(user_id, job_id)
                new_status = "expired" if row["status"] in TERMINAL_STATUSES else row["status"]
                async with pool.acquire() as conn:
                    await conn.execute(
                        """UPDATE public.jobs
                           SET retention_deleted_at = now(),
                               status = $2,
                               updated_at = now()
                           WHERE id = $1""",
                        row["id"],
                        new_status,
                    )
                logger.info("retention delete: job=%s objects=%d status=%s", job_id, count, new_status)
                deleted += 1
            except Exception as exc:
                logger.error("execute_retention_deletions: job=%s failed: %s", job_id, exc)
                # Do not raise — next run retries.
        logger.info("execute_retention_deletions: %d job(s) expired", deleted)
        return deleted

    async def retention_cron(ctx: dict | None = None) -> dict:
        """Entry point registered in WorkerSettings.cron_jobs — runs both passes sequentially."""
        warned = await send_retention_warnings(ctx)
        expired = await execute_retention_deletions(ctx)
        return {"warned": warned, "expired": expired}
    ```

## Threat Model

Trust boundaries: (1) cron (service role) → jobs + users tables + R2; (2) user → PUT /user/retention; (3) effective-date guard protects pre-policy data.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10.05-01 | Information loss (wrong user data deleted) | execute_retention_deletions | mitigate | Cron query joins jobs → users on user_id and uses each user's own data_retention_days. delete_job_objects is scoped to the `users/{user_id}/jobs/{job_id}/` prefix derived from the same row — impossible to delete another user's keys unless the row itself has a corrupt user_id FK, which the FK constraint prevents. |
| T-10.05-02 | Retention bypass via job-recreate loop | jobs creation after deletion | accept | Recreating a job to "refresh" the retention clock is acceptable (user must re-upload + re-dispatch — cost real GPU money). Policy is explicit in 10-CONTEXT.md: clock is from creation, not last access. Not a defect. |
| T-10.05-03 | Retroactive deletion of pre-policy data | cron SELECT | mitigate | Every query filters `j.created_at > policy_effective_from`. The singleton `retention_policy` row was seeded at migration time, so jobs older than migration apply are exempt. Users can opt-in to retroactive cleanup in a future release — out of scope here. |
| T-10.05-04 | Tampering (malicious retention reduction of other users) | PUT /user/retention | mitigate | Endpoint uses `Depends(get_current_user)` → WHERE id = user_id from JWT. Value is validated server-side (30 ≤ n ≤ 365). Users can only shorten their own retention. DB CHECK constraint is a second line of defense. |
| T-10.05-05 | Denial of service (cron deletes active work) | execute_retention_deletions | mitigate | Explicit `AND j.status != 'running'` in the SQL. Running jobs are exempt by design — cron does not interfere with live GPU work. Terminal-only status updates preserve history. |
| T-10.05-06 | Silent failure (email never sent but warning flag set) | send_retention_warnings | mitigate | Order: call send_retention_warning_email FIRST (wraps _send_email_safely which logs but does not raise). Only stamp retention_warning_sent_at AFTER the call returns. If email sending raises unexpectedly (resend.Emails.send isn't in the safe branch), the `except` logs and the row is NOT marked sent — cron retries next day. |
| T-10.05-07 | Race between user retention increase and next-day deletion | PUT /user/retention + cron | mitigate | A user extending retention from 90 → 180 days on day 89 results in the cron skipping deletion on day 90 (query recomputes the interval against the new column value every run). Acceptable: last-write-wins. A user shortening retention (180 → 30) may immediately expose data to deletion — documented behavior; frontend PrivacyTab shows a warning toast "Shortening retention may delete older jobs at the next daily run." |
